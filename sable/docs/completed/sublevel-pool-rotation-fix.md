# 分池原木朝向错误复盘

2026-09-07：用户游戏内复测确认原木朝向已修复。

## 问题根因

错误位于 `tools/sublevel-block/model-templates.ts` 的 `poolSlotOrientation()`：迁移时没有保留 TreePhysics 已验证的条件选择写法，而是生成了多个三元条件结果相加的旋转表达式。

- 旧写法：分别求出每个家族的 `条件 ? 角度 : 0`，再用 `+` 把结果相加。
- 修复写法：相同角度的家族条件用 `||` 合并，再通过条件分支选择一个角度；不同角度使用嵌套条件选择。这与 TreePhysics 原木、附件动画的写法一致。

旧表达式虽然在离线计算中得到正确角度，但在实际 Bedrock 分池动画中没有得到预期朝向，水平原木显示成了竖直原木。改回基准的条件选择方式后，游戏复测通过。**已确认的根因是分池旋转表达式的生成写法，不能据此认定分池架构不可用或 TreePhysics 无法泛化。**

这次修复保留了原有分池规则、家族编码、骨骼和旋转角度，仅改写表达式并重新生成资源。引擎内部具体如何导致旧写法失效尚未验证，不把表达式长度上限、精度或解析器内部缺陷写成已知原因。

## 为什么多次没有发现

1. 状态捕获、持久化和实体属性中的轴向数据本来就是正确的，反复检查这些环节无法暴露客户端动画执行差异。
2. `tools/verify-sublevel-parity.mjs` 的 `resourceEvaluator()` 用 JavaScript `new Function` 计算 Molang 表达式；补充使用的第三方 Molang 解释器也不是 Bedrock 客户端。旧求和写法在这些环境中能算出正确结果，所以离线对照一直通过。
3. 骨骼和纹理面变换的离线比较也依赖这些计算结果。因此，增加比较项目仍然没有检验实际失败的环节：原生客户端如何执行生成的动画。
4. 早期没有尽早把分池与独立模型放进同一个游戏场景对照，还将原木与箱子的朝向现象一起追查，扩大了排查范围。直到两排相同方块分别走两条路径，才将原木问题收窄到分池表达式。

**排查上的关键错误，是把数学等价和离线测试通过当成了 Bedrock 实际渲染等价。** 后续泛化动态旋转时，应保留 TreePhysics 已验证的条件选择结构，并用同场景的游戏内对照确认结果。

## 验证范围

用户确认同一游戏版本下 TreePhysics 正常；修改前两排原木朝向不同，修改后原木问题修复。两排箱子各自包含四个不同朝向，并且两排一一对应；这个结果只说明两条路径的箱子表现一致，不代表之前报告的箱子绝对朝向问题已解决。
