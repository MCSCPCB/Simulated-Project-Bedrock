# 子世界首次显示延迟修复

2026-09-10：用户报告新放置的子世界方块及从世界转换的方块有约一秒的显示延迟。本文记录代码中确认的发送空窗及其修复；客户端实际首帧时间仍需游戏内复测。

## 已确认的问题

`SubLevelRenderer.createRenderData` 和 `FancySubLevelModelRenderer.addBlocks` 都立即创建模型，并在下一轮 tick 释放初始姿态。代码没有设置一秒的显示等待；这一轮 tick 用于避免初始位置与姿态未同步时提前显示。

旧 Fancy 实现在创建当 tick 和下一 tick 发送输入，此后静止结构依赖 `INPUT_REFRESH_TICKS = 40` 的完整快照补发。如果客户端尚未接收渲染实体，最初的 `playAnimation` 输入未生效，模型会保持隐藏到下一次有效快照。

`ServerSubLevelContainer.tick` 还在入口使用 `currentTick % 20` 限制了整个巡检，包括 `renderData.sync()`，使完整快照的补发时间受到额外的巡检节奏影响。

在现有测试夹具中，假设客户端从实体出生后的第 2 tick 起才能接收输入，旧代码得到以下结果：

| 操作 | 等到下一次有效输入 |
| --- | --- |
| tick 0 转换世界方块 | 40 tick |
| tick 7 转换世界方块 | 53 tick |
| tick 20 向已有子世界放置方块 | 20 tick |

这些结果证明代码存在秒级恢复空窗。该模拟没有测量 Bedrock 客户端，不能将用户这次观察到的全部延迟确定归因于输入未被接收。

## 实现

复用 `playFancyModelInput` 和每个 `LiveModel.inputValues`，不增加新的输入协议或渲染资源。每批成功创建的模型在第 2、4、8、12、20 tick 各补发一次最新完整快照，取代旧的下一 tick 重复发送。初始姿态仍按原链路在下一 tick 释放。

五个延时回调由该批模型共享。回调只处理当前批次且仍登记在 `#modelByEntityId` 中的有效模型，因此新增方块的补发不会反复刷新已有模型；被删除、清空或替换的模型不会收到剩余回调。回调直接读取实时 `inputValues`，包括期间更新的模型状态、槽位占用、姿态和染色，不保留创建时的数据副本。

首次一秒内的补发结束后，继续使用每 40 tick 的常规完整快照，为新跟踪客户端提供恢复机会。此改动没有让静止结构永久逐 tick 发送动画。

管理器每 tick 调用渲染器的 `sync()`，由既有变化检测和刷新间隔决定是否发送。存档恢复、区域加载查询和实体完整性巡检仍每 20 tick 执行；没有把按方块遍历的区域查询提升到逐 tick。外部接入动态姿态时仍使用同一个 `playAnimation` 输入接口。

## 验证范围

`tools/verify-sublevel-parity.mjs` 的定时夹具现在按指定 tick 执行 `runTimeout`，覆盖以下行为：

- 客户端从出生后第 2、3、7、11、19 tick 起接收输入，转换、放置和渲染器重建均通过短期快照恢复显示，并保留草色和模型选择。
- 稳定模型不因另一个模型的启动补发而持续收到快照；移除子世界后不再向旧模型发送。
- 共享模型的箱盖状态修改和相邻槽位删除，在后续补发中保留；清空模型后剩余回调不再访问该实体。
- 姿态变化后的短期补发使用最新姿态；启动阶段结束后，静止帧不发送动画，40 tick 补发仍能恢复被清空的客户端输入。
- 管理器在两次巡检之间调用渲染同步，同时保持区域查询的 20 tick 间隔；tick 7 创建的渲染器在 tick 47 即可周期补发。
